## 17. 레벨 4 로보택시의 개발과 운영을 나눠 보기
{: #resource-17 }

### 학습한 모델을 로보택시 서비스로 연결하는 구조

GTC 특별 발표는 레벨 4 로보택시를 개발하려면 **클라우드 학습, 시뮬레이션, 차량 내부 연산**이 이어져야 한다고 설명한다. 클라우드에서 여러 상황의 데이터를 학습하고, 시뮬레이션에서 정책을 반복 실행한 뒤, 실제 차량에 통합해 센서 입력과 주행 지연을 검증한다. 현장에서 수집한 어려운 장면은 다시 데이터 선별과 시험에 활용할 수 있다.

### Hyperion, DRIVE AV, 운영 사업자의 역할

| 구성 | 맡는 역할 |
| --- | --- |
| Hyperion | 센서·차량용 컴퓨팅·네트워크와 안전 관련 요소를 통합할 레퍼런스 아키텍처 |
| DRIVE AV | 차량에서 주행 기능을 실행하는 소프트웨어 |
| OEM과 자율주행 개발사 | 차량 플랫폼과 센서·정책의 통합 및 검증 |
| 모빌리티 사업자 | 운행 지역과 서비스에 맞춘 차량 운영 |

발표에 나온 업체 협력은 같은 차량·센서 기반과 시험 절차를 여러 차량 프로그램에서 활용하려는 사례다. NVIDIA의 당시 발표는 Uber 등과의 전개 계획을 다루며, 계획과 특정 지역에서 운영이 확인된 상태는 구분한다.

발표에서 **Halos**는 Hyperion 위에서 하드웨어 보호, 운영체제와 미들웨어, 주행 판단의 안전 감시를 연결하는 체계다. 주행 모델이 궤적을 제안해도 별도의 감시 기능이 위험을 확인할 수 있다. 하드웨어 측의 중복 설계는 한 장치에 문제가 생겼을 때 필요한 기능이 동시에 끊기지 않도록 하는 접근이다. 공통 아키텍처를 쓰더라도 제조사와 소프트웨어 개발사 사이에 어떤 부분의 검증을 누가 맡는지 정해야 한다.

개발 도구 소개에서는 공개 데이터로 실패 후보를 찾고, NuRec으로 기록 장면을 복원해 자차의 위치가 달라질 때도 관측을 다시 그리는 예가 나온다. 학습·시뮬레이션과 차량 운행이 연결되는 이유는 현장에서 발견한 사례를 새 시험으로 만들고, 개선한 정책을 같은 조건에서 다시 비교할 수 있기 때문이다.

### 레벨 4에서 함께 봐야 할 시험 조건

레벨 4는 **정해진 운행설계영역(ODD)**에서 주행 시스템이 주행 작업과 필요한 비상 대응을 담당하는 수준이다. ODD를 지역, 도로 유형, 속도, 기상 등의 조건으로 구체화하면 무엇을 시험하고 어떤 조건에서 운행을 중단해야 하는지 정할 수 있다. 같은 정책을 다른 도시나 차량에 적용할 때는 센서 배치, 지역 도로 특성, 실제 운영 절차가 달라질 수 있으므로 차량 통합과 안전 평가가 별도로 필요하다.

## 18. 픽셀 단위로 보는 주행 장면의 구성
{: #resource-18 }

### 바운딩 박스와 픽셀 수준 인지

바운딩 박스는 물체가 들어 있는 사각형을 제공한다. 공사 콘, 인도와 도로의 경계, 바닥에 놓인 물건처럼 실제 모양이 복잡하면 사각형 내부에서도 물체와 배경을 구분할 필요가 있다. 2019년 DRIVE Labs 사례는 카메라 영상의 각 픽셀을 기준으로 장면을 이해하는 **파놉틱 세그멘테이션**을 소개한다.

- **시맨틱 세그멘테이션**은 도로, 보행자, 차량과 같이 픽셀의 범주를 알려준다.
- **인스턴스 세그멘테이션**은 같은 차량 범주의 픽셀도 어느 개별 차량에 속하는지 분리한다.
- **파놉틱 세그멘테이션**은 도로 같은 배경 범주와 구별할 수 있는 개별 객체를 한 장면 표현에 담는다.

### 여러 출력이 같은 인지 모델에서 만들어지는 이유

NVIDIA는 하나의 다중 과제 신경망으로 픽셀의 범주와 개별 객체를 추론한 사례를 소개한다. 개별 물체의 윤곽을 알면 물체 추적에 활용할 수 있고, 픽셀별 거리 추정과 결합하면 3D 위치를 더 자세히 파악할 수 있다. 영상 미리보기의 위쪽은 영역·객체 범주를, 아래쪽은 같은 범주 내의 개별 객체를 구분하는 모습을 보여준다.

### 발표의 성능 수치와 E2E 범위

공식 글은 당시 사용한 차량 내 DRIVE AGX에서 **프레임당 약 5 ms**의 인지 추론을 보고한다. 이 수치는 해당 인지 신경망의 실행 결과다. 주행 계획이나 제어까지 포함한 차량 전체의 반응 시간과는 측정 범위가 다르다. 이 사례에서 E2E는 카메라 입력에서 픽셀 단위 인지 출력까지를 뜻하고, Alpamayo의 주행 정책은 카메라 관측에서 궤적 생성까지를 다룬다.

## 19. 시나리오 시험과 센서 시험을 연결하기
{: #resource-19 }

### 시험하고 싶은 상황을 객체 수준에서 정의하기

Foretellix는 **Foretify**에서 어떤 상황을 생성하고, 어떤 조건을 변화시키며, 결과를 어떤 기준으로 볼지 관리하는 사례를 소개한다. 객체 수준의 시뮬레이션에는 도로, 자차, 주변 차량이나 보행자의 위치와 행동을 표현할 수 있다. 예를 들어 합류 차량의 속도와 진입 시점, 자차의 초기 속도를 바꾸면 비슷해 보이는 합류 상황에서도 서로 다른 위험도를 만들 수 있다.

### 같은 상황을 센서 입력까지 포함해 시험하기

객체 수준 시험에서 시스템에 이미 알려진 객체 위치를 쓰면 계획·제어를 살펴보기 좋다. 카메라 같은 실제 관측을 입력으로 쓰는 주행 시스템에는 **그 객체가 센서에서 어떻게 보이는지**도 필요하다. 영상이 소개하는 Omniverse Sensor RTX 연동은 객체와 움직임으로 정의한 시험 환경에서 물리 기반 센서 관측을 생성하는 방향이다. 관련 Foretellix 자료는 Cosmos Transfer를 이용해 관측 조건을 넓히는 통합 사례도 설명한다.

### 시나리오 커버리지와 판정 기준

시뮬레이션의 장점은 같은 위험 상황을 반복하고 일부 조건만 바꿔 비교할 수 있다는 것이다. 예를 들어 보행자 횡단 시험에 가림, 야간 조명, 자차 속도 차이를 조합하고, 충돌 여부와 함께 최소 거리·제동 개시 시점을 볼 수 있다. 화면에서 보행자 인지가 늦었는지, 충분히 일찍 인지하고도 제동 결정이 늦었는지 살펴보면 인지와 주행 정책을 구분해 분석할 수 있다. 많은 장면을 시험하는 것에 더해, **어떤 위험 조건을 검증했고 무엇이 아직 비어 있는지** 추적하는 것이 도구의 목적이다.

## 20. 안전 표준과 안전 근거를 구분하기
{: #resource-20 }

### 위험의 원인에 따라 적용하는 안전 관점

| 표준 | 패널이 다룬 범위 | 사례 |
| --- | --- | --- |
| ISO 26262 | 차량 전기·전자 시스템의 오작동으로 발생하는 위험 | 센서나 통신 장치의 고장으로 필요한 관측이 끊김 |
| ISO 21448(SOTIF) | 고장이 없어도 의도된 기능의 한계에서 생기는 위험 | 강한 역광이나 가림 때문에 정상 카메라가 객체를 충분히 구별하지 못함 |
| ISO/PAS 8800 | 차량 내 AI 구성요소와 관련된 안전 활동 | 학습 데이터의 범위와 모델 한계, 검증 자료를 관리 |

실제 시스템에서는 고장과 관측 한계가 함께 나타날 수 있다. 표준은 각 위험을 어떤 요구사항과 개발·검증 활동으로 관리할지 공통으로 이야기할 기준을 제공한다.

### 안전 논증과 검증 증거를 연결하는 과정

**안전 논증(safety case)**은 정해진 운행 조건에서 차량이 충분히 안전하다는 주장과 이를 지지하는 요구사항·시험 결과를 연결한다. 개발 단계에서 목표와 요구사항을 구성요소에 내려보내고, 시험 단계에서 해당 요구사항을 각각 검증한 뒤 통합 결과를 확인하는 V 모델이 설명된다. 학습 모델을 쓰면 어떤 데이터로 학습했는지, 독립된 시험 데이터가 무엇인지, 모델 변경이 기존 안전 요구에 영향을 주는지 추적하는 절차도 필요하다.

### 독립 평가의 범위

패널은 요구사항 추적성, 변경 관리, 정기 감사, 독립된 출시 검토 조직을 설명한다. TÜV Rheinland 사례는 NVIDIA의 레벨 4 **안전 관리 계획**을 대상으로 한 평가였다. 시스템을 개발하는 절차를 평가한 결과와 개별 차량이 모든 운행 조건에서 안전하다는 주장은 다르다. 안전 논증을 읽을 때는 평가 대상이 개발 과정인지, 특정 구성요소인지, 정해진 ODD의 차량 전체인지 함께 확인해야 한다.
